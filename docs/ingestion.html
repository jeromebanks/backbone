Ingestion pipeline: from a CLI to a production feed

How documents get from client systems into the clinical abstraction at 500K–1M+ scale, with daily arrivals, multi-patient documents and real file formats, without giving up the prototype's guarantees: verified evidence, deterministic reconciliation, and reproducible results.

Measured on the prototype (31 documents, Claude Opus 5.5). All production figures below are estimates derived from these measurements.

The governing principle

Reconciliation is order-independent. Precedence follows document relationships (explicit corrections, copies, evidence tiers), never arrival time or document date. So the pipeline needs no ordering guarantees. A late correction, a resend that arrives after it, or the same file delivered twice all reconcile to the same result.

What the pipeline must guarantee instead:

  • Idempotent stages: every stage is keyed by (sha256, stage, version), so re-running it is a no-op.
  • At-least-once delivery: events may repeat; the idempotent stages absorb the repeats.
  • Nothing is lost: every document has a state row, and failures end in a visible, retriable dead-letter state.

The pipeline

Seven stages, connected by events. Click a stage to see its contract: what it consumes and produces, its idempotency key, what it scales with, and how it fails.

Document lifecycle

Every document has one row in document_jobs. Its state shows exactly where the document is, operators can query it, and it makes lineage auditable. Branches never lose documents: skipped and linked copies are kept for audit, and failures land in needs_rescan or dead_letter, where they can be retried.

Two extraction lanes

Both lanes share one extraction contract, prompt, content-addressed cache and model-routing policy. They differ only in latency and price.

Guarantees and mechanisms

Idempotency everywhere

Stage keys are content hashes plus versions. Duplicate uploads stop at a conditional S3 put; duplicate events are no-ops; batch results are loaded by custom_id.

Transactional outbox

Each stage writes its result and its outgoing event in one Postgres transaction. A relay publishes the event afterwards, so state and events can't diverge after a crash.

Coalesced reconciliation

patient.dirty is an upsert, drained after a debounce window: 20 documents for one patient become one reconcile. Each job records the claims watermark it read; anything newer re-marks the patient dirty. There are no locks and no lost updates.

No PHI in transit metadata

Events, queue messages, logs and traces carry references only (tenant, sha256, patient ID). Document text lives only in S3 (KMS, object lock) and Postgres.

Quality gates

A batch halts automatically when any of these rates drifts above its threshold: schema failures, unverified quotes, unidentified contacts, near-duplicates. It is then rolled forward or back deliberately, never silently.

Fairness and backpressure

A weighted queue per tenant and lane, with reserved interactive capacity. Workers autoscale on queue depth, and the target is keeping the LLM token bucket full. The real ceiling is model quota, not CPU.

Backfills & reprocessing

Backfill

A durable workflow pages through an S3 Inventory manifest (never a bucket listing) and submits to the bulk lane with checkpoints. It can be paused and resumed, and it is throttled per tenant.

Extractor or model change

First a shadow run on a stratified sample, scored against the gold set and diffed at the level of reconciled outcomes. Promote only if field accuracy holds, then re-extract only the affected document types. Old extractions are kept for reproducibility.

Rule change

Bump the ruleset version and re-reconcile affected patients in the background. No LLM calls are needed, and it takes milliseconds per patient ( ms measured).

Rollout

Each step ships on its own and keeps the existing tests and golden values green.

1

State machine inside the current codebase ~1–2 wks

Add a document_jobs table with per-stage idempotency keys. Hash once at intake. Runs locally on SQLite or Postgres.

Exit: the existing test suite passes; re-ingest touches 0 files; duplicate-delivery, shuffled-order and crash-injection property tests pass.

2

Object storage, events, two lanes ~3–4 wks

S3 intake, transactional outbox, Temporal workflows, the interactive lane with a token bucket, and the bulk lane via Message Batches.

Exit: a 50K-document backfill within budget; interactive p95 under 2 minutes.

3

Real formats and routing ~3–4 wks

PDF, OCR and HL7/FHIR normalization with coordinate maps; fax-bundle splitting; classification; near-duplicate linking; multi-patient documents.

Exit: the gold set covers PDF and fax; skip and link rates measured; no clinical document wrongly skipped in the audit sample.

4

Operate at scale ~3 wks

Fair queues, autoscaling on queue depth, quality gates, cost and lineage dashboards, a 1M-document load test with a stubbed LLM, plus a real-LLM calibration sample.

Exit: SLOs met under load; drift gates trip in fault-injection tests.

What we deliberately don't use (and when we would)

Graph database

The domain is a graph, but the queries are shallow (≤ 3 hops, within one patient) and dominated by temporal joins and bounded arithmetic. That is Postgres territory. Later, as a CDC-fed projection, for patient identity resolution or provider and billing network analytics.

RDF / triple store

In healthcare, interoperability comes from FHIR and standard codes, not SPARQL. We store SNOMED, LOINC and CPT codes and export FHIR (Provenance maps directly to claims and evidence spans). RDF would be a cheap derived export if a client ever requires it.

RAG for answers

Top-k retrieval can't guarantee completeness: one missed correction changes the result. Counts and compliance stay deterministic. Retrieval is used only as a labelled "retrieved, not computed" tier and for cross-patient candidate search, via pgvector in Postgres over verified claims.
